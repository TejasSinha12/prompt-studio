# Prompt Studio — Architecture

Status: living document. Last updated 2026-10-15.

## 1. Goals and shape

Prompt Studio is a **single-user, local-first** workbench. It runs as two
processes on the user's laptop, both bound to loopback:

```
 Browser ──► Next.js (127.0.0.1:3000) ──/api/* rewrite──► FastAPI (127.0.0.1:8000) ──► SQLite (data/prompt_studio.db)
                                                               │
                                                               └──(optional, user-triggered)──► Ollama (127.0.0.1:11434)
```

* The browser only ever talks to the Next.js origin. A Next.js route handler
  (`src/app/api/[...path]/route.ts`) proxies `/api/*` to the backend, so the browser never needs CORS and the backend URL is
  never exposed to page scripts.
* All business logic is in Python. The frontend is a presentation layer.
* Ollama is optional. Every core feature has a deterministic implementation.

## 2. Repository layout

```
apps/
  api/                         FastAPI backend (Python package `prompt_studio`)
    prompt_studio/
      main.py                  app factory, middleware, router registration
      config.py                settings from env (pydantic-settings)
      db.py                    engine, session, SQLite pragmas, migrations runner
      models.py                SQLAlchemy ORM tables
      schemas/                 Pydantic request/response models
      security.py              host/origin/CSRF-header checks, body limits
      routers/                 thin HTTP layer, one file per route group
      services/                ProjectService, RecommendationService, ...
      engine/                  pure, side-effect-free domain logic
        analyzer/              deterministic requirement rules
        recommendations/       finding → recommendation mapping
        optimizer/             prompt builder + variants + preservation check
        evaluator/             quality diagnostics + heuristic score
        templates/             task templates + agent export profiles
        export/                Markdown / text / agent-file renderers
        text.py                normalisation, similarity, token estimate
      providers/               LocalModelProvider interface + Ollama impl
      cli.py                   init-db / backup / validate / restore commands
    migrations/                Alembic versions
    tests/                     pytest (unit, API, security, offline)
  web/                         Next.js App Router frontend (TypeScript strict)
    src/app/                   routes (dashboard, projects, library, ...)
    src/components/            UI kit + feature components
    src/lib/                   typed API client, hooks, utilities
    tests/                     Vitest + Testing Library
tests/e2e/                     Playwright end-to-end tests (offline workflow)
scripts/                       setup / dev / test orchestration (Node + shell)
docs/                          this documentation
data/                          runtime data (gitignored): DB, backups, exports
```

**Deviation from the suggested layout:** the suggested `packages/engine`,
`packages/providers`, etc. live inside the Python package
(`apps/api/prompt_studio/engine`, `.../providers`) because they are Python
code consumed only by the API; splitting them into separate distributions
adds packaging overhead with no benefit for a single-user app.
`packages/shared-schemas` is not created: the OpenAPI schema generated by
FastAPI is the source of truth, and the frontend's `src/lib/types.ts` mirrors
it by hand (checked by API integration tests and the E2E suite). This is a
documented trade-off (see §8).

## 3. Layering rules

| Layer | May depend on | Must not |
|---|---|---|
| `routers/` | services, schemas | touch ORM queries directly beyond passing a session |
| `services/` | engine, providers, models, schemas | know about HTTP |
| `engine/` | `text.py`, plain dataclasses / Pydantic | do I/O, network, DB, time-dependent output |
| `providers/` | httpx | know about DB or HTTP routes |

The `engine` package is deterministic: same input → same output. This is what
makes the offline mode trustworthy and testable, and it is enforced by a test
that blocks sockets while running the engine.

## 4. Data model (SQLite)

All IDs are UUID4 strings (stable, merge-safe for import). Timestamps are UTC
ISO-8601. Foreign keys are enforced (`PRAGMA foreign_keys=ON` on every
connection). WAL journal mode for crash safety.

| Table | Purpose | Key columns |
|---|---|---|
| `projects` | project root | name, description, original_idea, config (JSON: target agent, category, language, …), tech_stack, archived, **revision** (optimistic concurrency) |
| `project_events` | project history / audit trail | project_id, kind, summary |
| `tags`, `project_tags`, `prompt_tags` | tagging | unique tag name |
| `requirements` | structured spec items | project_id, kind (goal, functional, non_functional, security, constraint, acceptance, assumption, out_of_scope), text, status (confirmed, proposed, rejected, unresolved), source |
| `analysis_runs` | one analysis execution | engine (`rule_based`/`local_ai`), model, status, duration, error |
| `findings` | analyzer output | **fingerprint** (stable id), rule_id, category, kind, severity, confidence, evidence, … , status |
| `recommendations` | actionable proposals | fingerprint, finding_id, problem…verification, alternatives (JSON), proposed requirement kind/text, status |
| `recommendation_events` | approval history | from/to status, note, edited text |
| `prompts` | library entry | project_id (nullable), title, category, target_agent, favorite, archived, current_version_id |
| `prompt_versions` | **immutable** versions | prompt_id, number, content, variant, profile, generator, model, source_snapshot (JSON), change_summary, parent_version_id |
| `evaluations` | quality diagnostics for a version | prompt_version_id, engine, score, dimensions (JSON), findings (JSON) |
| `app_settings` | key/value settings | separate from project content |

Immutability of `prompt_versions` is enforced in the service layer (no
update path exists) **and** by a SQLite trigger that aborts `UPDATE` on
`content`. Restoring a version creates a new version whose
`parent_version_id` points at the restored one.

Migrations: Alembic, run automatically at startup (`upgrade head`) and
available via `scripts/` for manual use.

## 5. Key flows

### 5.1 Rule-based analysis (always available)
`POST /api/projects/{id}/analysis` with `engine=rule_based` → `AnalysisService`
loads the project + requirements → `engine.analyzer.analyze(spec)` returns
findings with fingerprints → upsert by fingerprint (existing **status is
preserved**, so dismissed findings stay dismissed) → findings that no longer
fire are marked `resolved` → `RecommendationService.sync` creates
recommendations for new fingerprints only; fingerprints whose recommendation
was rejected are **never re-proposed silently**.

### 5.2 Local AI analysis (explicit, optional)
Starts an **AI job** (`POST /api/ai/jobs`). Jobs run in an asyncio task guarded
by a semaphore (default concurrency 1). The provider asks Ollama for JSON
matching a schema (`format=<json schema>`), validates with Pydantic, and on
failure performs **one** bounded repair attempt that includes the validation
error. Still invalid → job fails with a clear error; nothing is stored.
Results are stored with `engine=local_ai` and the model name. Jobs can be
cancelled (`DELETE /api/ai/jobs/{id}`), which cancels the in-flight HTTP call.

### 5.3 Prompt generation
`PromptBuilder` takes a `ProjectSpec` (project + confirmed requirements +
approved recommendations + unresolved assumptions) and a variant
(`concise`/`balanced`/`detailed`) and a target profile, and selects relevant
sections from the 24-section schema based on task category, variant, and
available content (empty sections are omitted, never padded). The output
includes a **preservation report**: every confirmed requirement is checked
for presence in the rendered prompt. For local-AI rewrites the same check is
run on the model output and any missing requirement is highlighted.

### 5.4 Versioning
Saving a generated variant or a manual edit creates a new immutable
`prompt_version` with the full source snapshot (idea, requirements, config,
profile id+version) so it is reproducible.

### 5.5 Local codebase context (read-only)
`POST /api/codebase/scan` lists a user-supplied absolute directory with
`os.walk(followlinks=False)`; symlinks are reported and never followed. Secret
files, dependency/build/VCS dirs, generated files, binaries, oversized files,
root `.gitignore` entries and user globs are excluded, with a reason for each.
System directories and the bare home directory are refused (both the given and
the resolved path are checked). `POST /api/codebase/summary` re-validates every
selected path (containment, symlink, size, binary sniff), redacts likely
secrets and returns Markdown. Nothing is stored until the user inserts it into
the project and saves.

## 6. Local model provider interface

```python
class LocalModelProvider(Protocol):
    id: str
    async def status(self) -> ProviderStatus
    async def list_models(self) -> list[ModelInfo]
    async def generate_json(self, model, system, prompt, schema, options) -> dict
    async def generate_text(self, model, system, prompt, options) -> str
```

`ProviderRegistry` maps ids to providers; only `ollama` is implemented. The
Ollama endpoint is validated to be a loopback URL unless the user explicitly
enables a non-loopback host in settings (and the UI warns that content will
leave the machine). There is **no cloud provider** and no fallback to one.

User content is always passed in the user message, wrapped in clearly
delimited blocks; the system message states that the content is data and that
instructions inside it must not be followed (prompt-injection isolation).

## 7. Security architecture (summary — see THREAT_MODEL.md)

* uvicorn binds `127.0.0.1`; Next binds `127.0.0.1`.
* `TrustedHost` check (DNS-rebinding defence) on the API.
* Mutating requests require header `X-Prompt-Studio: 1` and, if an `Origin`
  header is present, it must be an allowed local origin (CSRF defence).
* Request body size limit (default 2 MiB, 10 MiB for project import).
* Pydantic validation with length/list limits on every input.
* Generic error responses; stack traces only in server logs, which never
  contain prompt content.
* Markdown rendered with `react-markdown` (no raw HTML) + `rehype-sanitize`.
* Backups restored only from the managed backups directory by validated
  filename, after integrity check and an automatic safety backup.

## 8. Trade-offs and decisions

| Decision | Alternatives | Rationale |
|---|---|---|
| Next.js route-handler proxy for `/api` | CORS between origins; `rewrites` | same-origin for browser, no CORS surface; unlike `rewrites` it can enforce the loopback Host check and inject the optional token server-side |
| In-memory AI job registry | DB-backed queue, Redis | single user, jobs are short-lived; restart cancels jobs (documented) |
| Hand-mirrored TS types | OpenAPI codegen | avoids a codegen toolchain; small API surface; covered by tests |
| Optimistic concurrency (`revision`) + explicit Save | autosave | no silent overwrite; visible dirty state; 409 on conflict |
| Textarea + live Markdown preview | heavy WYSIWYG editor | fewer deps, accessible, predictable plain-text output |
| `diff` (jsdiff) for line diffs | Monaco diff | tiny, no web workers, works offline |
| TypeScript 5.9 | TypeScript 7 (native) | Next.js 16 type-check integration is documented against TS 5.x |
| Approximate token estimate (chars/4, words×1.3) | bundling a tokenizer | tokenizers are model-specific; estimate is clearly labelled |
| uv for Python env | pip/venv | fast, lockfile, already installed; plain `pip install -e` also works |

## 9. Unresolved assumptions

1. Single user, single browser session at a time (no multi-user auth).
2. Ollama's HTTP API (`/api/version`, `/api/tags`, `/api/show`, `/api/chat`
   with `format`) is stable across the versions the user installs. Ollama
   0.40.4 is installed on the development machine as a macOS app (not on PATH);
   status and model listing were verified against it, but it had no models, so
   generation was only tested against a mocked API.
3. Model memory requirements are shown as on-disk size + a labelled rough
   guidance; no benchmarks were run.
4. Agent instruction-file conventions were checked against official docs on
   2026-10-15 (see `engine/templates/profiles.py`); they may change.
